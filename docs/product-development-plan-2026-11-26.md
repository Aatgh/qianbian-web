# 千变 · 主动关心型生活 Agent 开发计划（2026-11-26）

> 目标：从“会回答的 Agent”升级为“长期懂你、会在合适时机主动关心你”的生活伙伴。
> 本文是开发执行计划，配合 `docs/proactive-care-plan-2026-11-26.md` 阅读。

## 一、现状盘点

### 已有（可复用）

- 后端：Java 若依 3.9.2 + Node bridge；短信登录、Cookie 会话、SSE 流式、会话/消息、技能市场/安装/发布、审批/提问、长期记忆、契合度、设备/连接器、IP 定位、Agent 工作区模块。
- 前端：手机端/电脑端已完成第一轮视觉重构；登录、对话、历史、技能、设备、账号、工作区入口可用。
- 部署：`agiqianbian.com` / `admin.agiqianbian.com`，ECS 与 Shua 同机；Docker + nginx + acme 证书。
- 测试：Playwright 82 通过 / 4 跳过。

### 缺口（本计划要补）

- 没有“生命循环”：没有心跳、没有用户状态、没有主动事件、没有关心调度。
- 没有用户画像：只有零散记忆/契合度，没有结构化假设、证据、置信度和确认机制。
- 没有技能主动契约：技能只能被用户/Agent 回合内调用，不能定时/事件驱动。
- 没有内容源：新闻、天气实时降水、股票、健康数据都没有接入；技能内容也偏少。
- 没有 APK：步数、系统定位、通知权限都拿不到。
- 没有关心设置/关心消息中心/画像页/运营后台。
- 没有多设备 token（电脑+手机同时在线）。

## 二、产品架构

```text
┌─────────────── 信号层 ───────────────┐
│ APK DeviceBridge：步数/位置/设备信息    │
│ 后端事件：聊天/技能/审批/活跃            │
│ 外部内容：天气/新闻/股票/健康            │
└──────────────────┬───────────────────┘
                   ↓
┌─────────────── 理解层 ───────────────┐
│ LifeSignalService：归一化、日聚合       │
│ UserProfileService：假设/证据/置信度     │
│ Memory/Affinity：语气、偏好、长期关系    │
└──────────────────┬───────────────────┘
                   ↓
┌─────────────── 决策层 ───────────────┐
│ CareRuleEngine：规则/事件触发           │
│ SkillCareRuntime：技能的 proactive 钩子 │
│ CuriosityPlanner：该问什么、何时问       │
└──────────────────┬───────────────────┘
                   ↓
┌─────────────── 表达层 ───────────────┐
│ CareComposer：LLM + 人设 + 记忆 + 事实   │
│ CareScheduler：频控/静默/去重/预算       │
│ 站内「千变的关心」+ 推送                 │
└──────────────────┬───────────────────┘
                   ↓
              用户反馈 → 记忆/画像 → 下一轮更懂
```

### 三种时钟

1. **心跳（3–5 分钟，服务端）**：扫描 `next_wake_at`，只做廉价判断，不调 LLM。
2. **认知（事件驱动）**：用户消息、技能 watcher 事件、约定到期、画像假设触发时才调模型。
3. **表达（严格限频）**：默认每天 1–2 条主动消息，静默 23:00–08:00。

## 三、数据模型（新增）

```text
qb_life_signal         用户每日信号（步数、位置、天气、活跃）
qb_care_plan           用户订阅的关心计划（技能/主题/频率/输入）
qb_care_candidate      技能/规则产生的候选事件（去重、重要性、过期）
qb_care_event          已决策的关心事件（调度、发送、回复）
qb_care_preference     关心设置（开关、静默、每日上限、主题、语气）
qb_user_profile        用户画像维度（值、置信度、状态、敏感级别）
qb_profile_evidence    画像证据（来源、权重、时间）
qb_skill_proactive     技能主动能力声明（也可放 SKILL.md front matter）
qb_care_message        可复用 qb_message，固定「千变的关心」会话
qb_daily_digest        早报/晚报聚合（天气+新闻+卦象+股票）
```

所有表带 `user_id`、时间、软删；敏感字段加密；不做跨用户聚合。

## 四、技能 = 可订阅的关心能力

技能 manifest 增加 `proactive` 契约：

```json
{
  "proactive": {
    "capabilities": ["news_digest", "breaking_news"],
    "inputs": ["topics", "frequency", "quiet_hours"],
    "triggers": [
      { "type": "schedule", "default": "08:30" },
      { "type": "event", "event": "breaking_news", "min_importance": 0.8 }
    ],
    "maxPerDay": 2,
    "cost": "low",
    "disclaimer": "新闻内容以来源为准"
  }
}
```

Agent 不硬编码每个技能：

- 发现技能支持主动能力；
- 和用户做一次“开通对话”，学习偏好；
- 存储 `qb_care_plan`；
- 定时/事件触发时调用技能 watcher，产生候选；
- 用用户语气组织消息。

## 五、开发阶段与排期

### Phase 0：基础设施（2 周）

- 数据表 + 迁移脚本；
- `LifeSignalService`、`CareRuleEngine`、`CareScheduler` 骨架；
- 心跳扫描（Quartz 或独立 Node worker），`next_wake_at`；
- 关心设置表/接口；
- 固定「千变的关心」会话；
- 测试账号 + 模拟信号接口（不依赖 APK）。

验收：测试账号能按模拟步数/天气触发关心消息；频控/静默/去重生效。

### Phase 1：技能主动关心 MVP（3–4 周）

- 技能 `proactive` 契约 + `SkillCareRuntime`（只读/网络白名单，写操作仍审批）；
- 先接两个技能：
  - **天气**：早报 + 降雨提醒（和风天气）；
  - **新闻**：每日摘要 + 大事候选（商业新闻 API）；
- 技能开通对话（新闻分类、天气提醒、频率）；
- 关心消息中心 + 设置页（前端）；
- 运营后台：关心事件查看、频率/模板配置、用户反馈。

验收：真实天气/新闻源触发；用户可开关、调频率；消息不重复、不越静默。

### Phase 2：APK 壳与真实信号（3–4 周）

- Capacitor 壳 + `DeviceBridge` 原生插件：
  - 系统定位、步数（`TYPE_STEP_COUNTER` + `ACTIVITY_RECOGNITION`）、通知权限、设备信息；
  - 后台同步（WorkManager/前台服务）、厂商省电引导；
- 后端 `/app/device/signals`，日聚合，不存原始传感器流；
- 步数平台期规则、雨天关心；
- Android 优先；iOS（CMPedometer/HealthKit）下一阶段。

验收：真机日步数、位置、天气关心可用；后台功耗可控。

### Phase 3：用户画像与个性化（3–4 周）

- `qb_user_profile` / `qb_profile_evidence`；
- 每日批处理：步数趋势、活跃时段、话题/技能兴趣、语言风格；
- 假设生成（规则 + LLM 结构化抽取），带证据/置信度；
- 好奇心预算：每天最多 1 个画像问题；
- 确认/否认/纠正 → 更新画像；
- 画像页：用户可见、可删；
- 个性化：语气、时机、内容、技能推荐。

验收：至少 3 类假设（是否锻炼、作息、兴趣）能问、能确认、能影响关心文案。

### Phase 4：内容/商业/规模（4–6 周）

- 更多技能：算命（现有技能接入）、股票（合规行情源，只做提醒不做建议）、健身/饮食计划；
- 早报/晚报聚合；
- 推送通道（厂商推送/极光/APNs）；
- 多设备 token、电脑+手机同步；
- 订阅/会员/付费点设计；
- 数据分析、A/B、成本控制。

## 六、前端工作

- 关心设置页：总开关、频率、静默、主题、技能订阅；
- 「千变的关心」会话 + 未读提醒；
- 画像页：“它认为你知道什么”、证据、删除；
- 推送权限引导、通知渠道设置；
- APK 壳（Capacitor）+ 原生权限页；
- 运营后台：关心事件、模板、频率、用户反馈、内容源配置。

## 七、我需要你协调的资源（按优先级）

### P0：现在就需要

1. **和风天气 API Key**：实时天气、降水、分钟级降水；备选高德天气。
2. **商业新闻 API**：要合法授权、中文、分类/热榜/突发；建议先谈天行数据/聚合数据做 POC，同时推进官方媒体合作；需要预算和合同主体。
3. **LLM 预算**：DeepSeek pro/flash 配额；一个便宜的 embedding 模型（BGE/阿里/DeepSeek）用于兴趣聚类。
4. **产品决策**：
   - 首批技能：天气 + 新闻（建议）；
   - 默认主动频率（建议每天 1 条）和静默时段（23:00–08:00）；
   - 关心消息放固定会话还是独立关心页；
   - Android 优先，iOS 排后。
5. **测试设备/账号**：至少一台 Android 真机（小米/华为/OPPO 各一台更好），用于后台/传感器/通知验证。

### P1：Phase 2–3 需要

6. **推送服务**：极光/个推/厂商推送账号；或先只做站内+本地通知。
7. **Android 原生开发资源**：Capacitor 插件/后台服务；如果内部没有，建议外包或招 1 名 Android 工程师。
8. **服务器/数据库扩容**：关心心跳、队列、画像批处理需要独立 worker（不要和 Shua 抢资源）；预算另开一台 ECS/RDS/Redis。
9. **设计资源**：关心卡片、画像页、APK 引导页；至少 1 名产品设计师。
10. **内容运营**：新闻分类/摘要质量、天气文案、运动饮食内容审核；需要 1 名内容/运营。

### P2：Phase 4 需要

11. **股票行情授权**：合规数据源（交易所/持牌供应商），只做行情提醒，不做投资建议；需要法务评估。
12. **健康数据合规**：Health Connect/HealthKit、隐私政策、单独同意；iOS 开发者账号。
13. **应用商店账号**：华为/小米/OPPO/vivo/应用宝 + Apple Developer；软著、隐私政策、备案（已有 ICP）。
14. **法务/合规**：PIPL、敏感个人信息、新闻版权、投资/健康免责声明。
15. **客服/危机干预流程**：用户出现自伤/极端情绪时的人工跟进（可复用 Shua 的用户关怀经验）。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 过度关心变骚扰 | 默认低频、静默、每日上限、反馈降频、A/B |
| Android 后台/传感器受限 | 前台服务/WorkManager、厂商引导、iOS 历史步数兜底 |
| 新闻版权/假新闻 | 商业授权源、多源校验、重要性评分、不编造 |
| 股票合规 | 只做行情提醒，不做建议，持牌数据源，免责声明 |
| 隐私/敏感信息 | 最小化、加密、画像可见可删、单独同意、PIPL |
| LLM 成本 | 心跳不调模型、小模型初筛、缓存、每用户预算 |
| 与 Shua 同机资源冲突 | 独立 worker/DB/Redis，限流，监控 |
| 产品依赖感/伦理 | 不模拟脆弱、不情感操纵、边界与透明 |

## 九、成功指标

- 主动关心开启率、消息回复率、关闭/免打扰率；
- D7/D30 留存、日均对话轮次、技能使用；
- 画像确认率（用户确认/否认的比例）、画像纠正率；
- 每用户每日 LLM 成本、每条关心成本；
- 投诉率、静默违规数、事实错误率。
